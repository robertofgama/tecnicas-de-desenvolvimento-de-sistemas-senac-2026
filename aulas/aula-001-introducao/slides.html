…mas toda analogia tem limite

  • O "garçom" não é uma pessoa: é um protocolo, um conjunto de regras de comunicação
  • A "cozinha" atende milhares de mesas ao mesmo tempo
  • O "salão" também pensa: a tela pode conferir um campo vazio antes de chamar o garçom
  • A "despensa" tem regras rígidas: nada entra sem etiqueta e sem lugar definido
Este slide é para quem já programa não achar a analogia simplista demais. Ela serve como mapa, não como definição.

A viagem de um pedido

Ana, do comercial, registra um pedido da Agro Silva: 2 plantadeiras e 10 kits de discos de corte. Ela clica em Salvar pedido.

O que acontece entre o clique e o “Pedido nº 7 salvo”?

Este é o mapa da aula. Cada parada é um tema do curso. Vamos seguir o pedido da Ana do clique até o banco e de volta.
Parada 1 · A tela

HTML: a estrutura

Diz o que existe na página: um formulário, campos, um botão.

É o esqueleto. Sem estilo, sem comportamento.

HTML não é linguagem de programação, é de marcação: descreve o conteúdo. As "tags" dizem o papel de cada pedaço.
Parada 1 · A tela

CSS: a aparência

Diz como as coisas aparecem: cores, tamanhos, espaçamentos, posições.

O mesmo HTML pode ter visuais completamente diferentes.


form {
  display: flex;
  flex-direction: column;
  gap: 12px;
}

button {
  background: #2563eb;
  color: white;
  border-radius: 8px;
}
Analogia: o HTML é a planta da casa, o CSS é a pintura e a decoração.

Parada 2 · A lógica

JavaScript: o comportamento

Diz o que acontece quando a Ana clica: pega os dados, confere, envia.

Agora sim, uma linguagem de programação.


const form = document.querySelector('#form-pedido');

form.addEventListener('submit', (evento) => {
  evento.preventDefault();
  const dados = new FormData(form);
  console.log('Salvando pedido de', dados.get('cliente'));
});
HTML = estrutura, CSS = aparência, JS = comportamento. É a tríade do front-end. O JS reage a eventos: clique, digitação, carregamento.
Parada 2 · A lógica

JavaScript moderno (ES6+)

Funções de seta (=>), desestruturação ({ qtd, preco }), map e filter: a base de tudo o que faremos em React.

Não é para entender a sintaxe hoje. Mostre a ideia: filter separa, map transforma. Isso aparece o tempo todo em React.
Parada 2 · A lógica

Esperar sem travar

Salvar o pedido leva um tempo: a resposta vem pela rede.

🍔 Como pedir lanche no balcão: você recebe uma senha e não fica parado esperando.

Promises e async/await


async function salvarPedido(pedido) {
  const resposta = await fetch('/pedidos', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(pedido),
  });
  return resposta.json();
}
Síncrono: um passo de cada vez, esperando cada um terminar. Assíncrono: dispara a tarefa demorada e continua; quando a resposta chega, o código retoma. O await marca o ponto de espera.
Parada 3 · Os componentes

React: a tela em peças de Lego

<App>

<ListaPedidos>

<ItemPedido>Nº 5 · Agro Silva
  • Cada pedaço da tela é um componente
  • Escrito uma vez, reutilizado muitas vezes
  • Mais fácil de manter em sistemas grandes
React é uma biblioteca JavaScript para montar interfaces. O ItemPedido é escrito uma vez e usado para cada pedido da lista.
Parada 3 · Os componentes

Props e estado

  • Props: o que o componente recebe de fora (cliente, total)
  • Estado (useState): o que o componente lembra e que, quando muda, redesenha a tela
Repare no map de novo: a lista de pedidos vira uma lista de componentes. Isso é renderização dinâmica.
Parada 3 · Os componentes

useEffect: falar com o mundo lá fora

“Quando a tela abrir, busque os pedidos no servidor.”

É aqui que o front-end chama a API: a próxima parada.


useEffect(() => {
  fetch('/pedidos')
    .then((resposta) => resposta.json())
    .then((lista) => setPedidos(lista));
}, []);
useEffect executa um efeito colateral: algo fora do desenho da tela, como buscar dados. O [] no fim significa "só uma vez, quando o componente aparece".

☕ Intervalo

15 minutos. Na volta, o pedido sai do navegador.

Marcar o horário de retorno no quadro.
Parada 4 · A rede

Requisição e resposta (HTTP)

🖥️ Navegador
da Ana
Requisição: POST /pedidos + dados do pedido
Resposta: 201 Created + pedido nº 7
🗄️ Servidor
da empresa

HTTP é o “idioma” da web: toda conversa é uma pergunta (requisição) seguida de uma resposta.

Esse é o garçom da analogia. Toda página que você abre é uma requisição HTTP. O navegador pede, o servidor responde.
Parada 4 · A rede

JSON: a comanda

O formato combinado para os dados viajarem.

Texto simples, legível por pessoas e por qualquer linguagem.


{
  "clienteId": 12,
  "itens": [
    { "produtoId": 3, "quantidade": 2 },
    { "produtoId": 8, "quantidade": 10 }
  ]
}
Note que viajam os números (ids), não os nomes. O servidor sabe quem é o cliente 12. JSON é praticamente a sintaxe de objetos do JavaScript.
Parada 4 · A rede

API é o cardápio: a lista do que se pode pedir ao servidor. REST é um padrão de organização, com substantivos no endereço e verbos HTTP para a ação. Códigos 2xx dão certo, 4xx são erro de quem pediu e 5xx são erro do servidor.
Parada 5 · O servidor

Node.js + Express

  • Node.js: JavaScript rodando fora do navegador, no servidor
  • Express: organiza as rotas, ou seja, qual código responde a cada endereço

const express = require('express');
const app = express();
app.use(express.json());

app.post('/pedidos', async (req, res) => {
  const pedido = await salvarNoBanco(req.body);
  res.status(201).json(pedido);
});

app.listen(3000);
A mesma linguagem do front-end, agora na cozinha. Isso é uma grande vantagem do curso: um só idioma do começo ao fim.
Parada 5 · O servidor

Middlewares e regras de negócio

requisição→ express.json()→ validarPedido→ criarPedido→ resposta
Middleware é um posto de checagem na fila. A regra "quantidade maior que zero" é uma regra de negócio: ela mora no servidor, porque a tela pode ser burlada.

Parada 6 · O banco

Chaves e relacionamentos

clientes
  • 🔑 id
  • nome
  • cidade
1 : N
pedidos
  • 🔑 id
  • 🔗 cliente_id
  • data
1 : N
itens_pedido
  • 🔗 pedido_id
  • 🔗 produto_id
  • quantidade
N : 1
produtos
  • 🔑 id
  • nome
  • preco
  • 1:N: um cliente tem muitos pedidos
  • N:N: um pedido tem muitos produtos, e um produto aparece em muitos pedidos (a tabela itens_pedido faz a ponte)
🔑 é a chave primária e 🔗 é a chave estrangeira, que aponta para outra tabela. É ela que impede um pedido de apontar para um cliente que não existe.
Parada 6 · O banco

SQL: a língua do banco


-- Gravar o pedido da Ana (o banco gerou o nº 7)
INSERT INTO pedidos (cliente_id, data) VALUES (12, '2026-10-05');
INSERT INTO itens_pedido (pedido_id, produto_id, quantidade)
VALUES (7, 3, 2), (7, 8, 10);

-- Consultar: quem comprou o quê?
SELECT c.nome, p.id AS pedido, pr.nome AS produto, i.quantidade
FROM pedidos p
JOIN clientes c     ON c.id = p.cliente_id
JOIN itens_pedido i ON i.pedido_id = p.id
JOIN produtos pr    ON pr.id = i.produto_id;
SQL é quase inglês: insira em, selecione de, junte. O JOIN usa as chaves para reconstruir a informação espalhada pelas tabelas.

E a viagem de volta

  1. O banco confirma: pedido nº 7 gravado
  2. O servidor responde 201 Created com o pedido em JSON
  3. O React atualiza o estado (setPedidos)
  4. A tela se redesenha: o pedido nº 7 aparece na lista

Tudo isso em menos de um segundo.

Fechar o ciclo. Perguntar à turma: em qual parada vocês acham que mais coisas podem dar errado?

Dinâmica: em que camada?

Vou mostrar problemas reais de sistemas. Em grupos, decidam: em que parada da viagem você começaria a investigar?

Cerca de 2 minutos por situação. Vale discordar: muitas vezes há mais de uma resposta defensável.

Formar grupos de 3 ou 4, misturando níveis da sondagem. Cada grupo responde e justifica antes de você revelar (seta para baixo/direita mostra a resposta).

Situação 1

“No celular, o botão Salvar pedido aparece cortado pela metade.”

TelaJavaScriptReactRedeServidorBanco
Tela (CSS). Problema de layout responsivo: Flexbox ou Grid não se adaptaram à largura do celular.
Pista: o problema só acontece em um tamanho de tela, e os dados estão certos.

Situação 2

“O total do pedido aparece como NaN na tela.”

TelaJavaScriptReactRedeServidorBanco
JavaScript. “Not a Number”: alguma conta recebeu texto ou um valor vazio no lugar de um número.
Pista: NaN é uma mensagem típica do JavaScript. Investigar o cálculo do total (map com qtd * preco).

Situação 3

“Um pedido foi salvo com quantidade −3.”

TelaJavaScriptReactRedeServidorBanco
Servidor (validação). A regra de negócio “quantidade maior que zero” precisa estar no back-end. A tela até pode avisar, mas o servidor é quem garante.
Discussão rica: a tela deveria barrar? Sim, mas não basta, porque qualquer um pode enviar uma requisição direto à API (Postman!). O banco também pode ter uma restrição como segunda linha de defesa.

Situação 4

“A lista de pedidos fica ‘carregando…’ para sempre.”

TelaJavaScriptReactRedeServidorBanco
Rede / API. A requisição não voltou: o servidor está fora do ar, o endereço está errado ou houve um erro sem tratamento.
Primeiro passo: abrir as ferramentas de desenvolvedor do navegador, aba Rede, e ver a requisição e o código de resposta.

Situação 5

“O pedido está no banco, mas não aparece na tela.”

TelaJavaScriptReactRedeServidorBanco
React (estado). Os dados chegaram, mas o estado não foi atualizado, ou o useEffect não buscou de novo.
A pista é "está no banco": a parte de baixo da viagem funcionou. O problema está na volta, no front.

Situação 6

“Excluíram um cliente e os pedidos dele ficaram apontando para ninguém.”

TelaJavaScriptReactRedeServidorBanco
Banco (chave estrangeira). Faltou a regra que liga pedidos.cliente_id a clientes.id e impede registros órfãos.
Relembrar o 🔗 do diagrama. Integridade dos dados é responsabilidade do modelo do banco.
